# Write the README spec
Create `docs/agents/image-readme.md`, the single source of truth for per-image `README.md` files. Write it in English as a reference doc (not issue prose), organized in these sections, with content taken from the issue's Solution (*Spec:* subsections):

1. **Purpose** — `<image>/<version>/README.md` is the Docker Hub full description of `darthjee/<image>`, pushed by `bin/script.sh push_description`. These rules apply to new READMEs and to any README being edited; existing deviations are fixed only when a README is next edited (hardcoded tags: #173-style cleanup).
2. **Skeleton** — the fenced skeleton block from the issue (title underlined with `=`, *About the image*, middle sections, *How to use*, *License* with "See the LICENSE file for more information.").
3. **About the image** — what it is; base image (link if `darthjee/`, never its version); default user/uid, working directory and owner; what the base provides; the legacy note wording for end-of-life bases (`> **Note:** This is a legacy image built on an old, end-of-life base (...).`), dropped when rebuilt. Source of facts: the Dockerfile, `home/` files, build-time scripts (e.g. `poetry_builder.sh`).
4. **Middle sections menu** — `Tools`, `Pre-installed packages`/`Pre-installed gems` (grouped with `###` when long), `Pre-cached packages`, `What is added`, `Included scripts`, `Usage example` (tool images), `Variants` (optional table); each with when to use it and its reference README.
5. **How to use** — tags link `https://hub.docker.com/r/darthjee/<image>/tags`; `FROM darthjee/<image>:<version>` Dockerfile example for dev/production, CircleCI executor YAML for `circleci_`, `COPY --from=darthjee/scripts:<version>` for tool images; production examples install main dependencies only; short edge-case sentences where relevant (virtualenv location and `poetry run`/`pipenv run`; when a pre-populated cache is bypassed).
6. **Versions and architectures** — no `darthjee/` tags (own or parent) and no package/tool versions, because `init` copies the README unchanged and only bumps `FROM` lines; exception: versions that are part of an upstream base's identity (e.g. Python 3.12, `circleci/python:3.7.2`). No architecture claims.
7. **Counterparts and families** — the six counterpart rules (intro wording, built-on vs. by-name-only, one-way links, mirrored hierarchies link parent and dev counterpart, dev README first and reused, family sync in the same PR, family push behavior).
8. **Docker Hub rendering** — absolute `https://` links and images only; 25,000-character `full_description` limit.
9. **Process** — README-only change: in place in the folder `version` points to (even an unreleased `init` folder), no `init`, no `version` bump, no `pre_build`/`build`/`test` (explicit exception to `docs/agents/contributing.md`'s CI checks); never edit older version folders; fixing an already-released version's README in place is fine. **Highlighted rule:** any change to an image's contents updates its README (and, for shared content, its counterparts' READMEs) in the same PR. Releases do not push descriptions; run `bin/script.sh push_description <image>`, which exits 1 until the whole family has READMEs. Testing: manual Docker Hub check.
10. **Reference examples** — links (relative, from `docs/agents/`) to `python_37/0.2.2/README.md` (minimal), `circleci_python_37/0.2.2/README.md` (legacy CircleCI counterpart by name), `node/0.2.2/README.md` (pre-cached), `rails_gems/2.1.1/README.md` (grouped gems), `ruby_node/1.5.0/README.md` (what is added + variants), `scripts/0.10.0/README.md` (tool image). Check each path exists at implementation time and use the folder `version` points to.
